> [!note] 红黑树是一棵**自平衡的二叉查找树**，它不追求"绝对平衡"，而是用**颜色**这个巧妙的维度换取更少的旋转次数，是工程界使用频率最高的平衡树之一。这篇笔记配合完整可运行的 C++ 代码（哨兵 nil + 循环修复实现），把"是什么、为什么、怎么做"三件事捋清楚，末尾还记录了几个编码调试时的真实踩坑经历。🎯

## 🌱 一、概念、性质与来龙去脉

### 🌳 1.1 起源：一条"平衡之路"

红黑树不是横空出世的，它是二叉查找树（BST）在"追求平衡"这条路上的一个**折中方案**：

![红黑树 1.png](<../pict/红黑树 1.png>)

> [!tip] 一句话理解取舍 AVL 树像个"完美主义者"，稍微失衡一点就要立刻纠正；红黑树更"佛系"一些，允许一定程度的不平衡（最长路径不超过最短路径的 2 倍），换来的是**插入/删除时旋转次数的大幅减少**——这正是它更适合"动态查找"（频繁增删）场景的原因。

**红黑树的实际应用** 🏭：

- 🔧 C++ `std::map` / `std::set`、Java `TreeMap` / `TreeSet` 的底层实现
- 🐧 Linux **CFS**（完全公平调度器）用红黑树管理可运行进程
- 📡 Linux **epoll** 用红黑树管理已注册的文件描述符（fd）

---

### 🔴⚫ 1.2 红黑树的五条性质

红黑树在 BST 的基础上，额外满足下面 5 条规则：

1. 🎨 每个结点**非红即黑**；
2. 👑 **【根叶黑-根】** 根结点必须是黑色；
3. 🍃 **【根叶黑-叶】** 每个"叶结点"（这里指真正意义上的空结点 NIL）是黑色；
4. 🚫 **【不红红】** 红色结点的两个孩子都必须是黑色（等价于：不存在两个相邻的红色结点）；
5. ⚖️ **【黑路同】** 从任一结点出发，到其子孙所有 NIL 叶结点的路径上，经过的黑色结点数目都相同——这个数目称为该结点的**黑高**（black-height）。

> [!note] 性质 4 + 5 ⇒ 近似平衡 这两条性质共同保证了：从根到任意 NIL 的**最长路径不会超过最短路径的 2 倍**。这就是红黑树能维持 O(log n) 查找/插入/删除的根本原因——树不可能长得"特别歪"。

---

### 🛡️ 1.3 一个关键设计：哨兵 nil

本实现用一个**共享的哨兵结点 `nil`** 代表所有空叶子，而不是用裸的 `nullptr`。

> [!tip] 为什么这么设计 所有"空结点"因此天然拥有颜色（恒为黑色），判断/访问一个空位置的颜色时不需要写 `if (p == nullptr)` 特判，插入、删除、旋转的代码可以**统一处理**，边界情况大大简化——这是教科书级红黑树实现的标准做法。删除算法里还有一个进阶用法：借用 `nil->parent` 字段临时记录"被删位置的父结点"，这个技巧在下面"删除"一节会详细拆解。

## 🧱 二、总体框架 & 头文件全貌（代码块 1️⃣）

### 📐 整体架构思路

延续 B 树模块的组织方式，采用**命名空间 + 类**，并且严格区分 public / private：

- **public** 🔓：`search` / `insert` / `remove` / `print` / `blackHeight` 这些对外契约，负责边界处理（空树、重复关键字）；
- **private** 🔒：`Node` 结点结构 + 左右旋、插入修复、删除修复等核心算法 helper，外部完全不需要知道内部是怎么转的。

三文件分工：

- `RBTree.h`：只放声明（接口）
- `RBTree.cpp`：真正的算法实现
- `main.cpp`：自动演示 + 交互菜单
- `Utils.h` / `Utils.cpp`：跨数据结构复用的安全输入函数 `getInt`（和 B 树项目共用同一份）

> [!note] 类型别名而非模板 `using KeyType = int;` 是有意为之的取舍：让"接口/实现/main 三文件分离"这件事更直观。如果想支持多类型共存，可以改造成 `template<typename KeyType> class RBTree`，代价是模板的实现通常要搬回头文件（或做显式实例化）。

#define RBTREE_ADT_H

#include <string>
#include <iostream>

namespace RBTreeADT {

    using KeyType = int;

    /// 结点颜色
    enum class Color { RED, BLACK };

    class RBTree {
    public:
        RBTree();
        ~RBTree();

        // 教学容器，禁用拷贝，避免多个 RBTree 对象浅拷贝共享/重复释放结点指针
        RBTree(const RBTree&) = delete;
        RBTree& operator=(const RBTree&) = delete;

        // ------------------------------------------------------------------
        // 公有接口区
        // ------------------------------------------------------------------
        bool search(KeyType key) const;
        bool search(KeyType key, std::string& locationDesc) const;
        void insert(KeyType key);
        bool remove(KeyType key);
        void print() const;
        bool empty() const;

        /// 计算根结点的黑高，并顺带校验"黑路同"性质（返回 -1 说明性质被破坏）
        int blackHeight() const;

    private:
        /**
         * @struct Node
         * 非叶结点：left/right 指向真实孩子或 nil；parent 指向真实父亲或 nil（根）。
         * 哨兵 nil：本身的字段一般不被访问，但删除算法会临时借用 nil->parent
         *           记录"被删位置的父结点"，仅在单次删除过程中有意义。
         */
        struct Node {
            KeyType key;
            Color color;
            Node* left;
            Node* right;
            Node* parent;

            Node(KeyType k, Color c, Node* l, Node* r, Node* p)
                : key(k), color(c), left(l), right(r), parent(p) {}
        };

        Node* nil;   ///< 哨兵结点：代表所有空叶子，恒为黑色

        // ==================== 查找：私有 helper ====================
        Node* searchHelper(KeyType key) const;

        void leftRotate(Node* x);
        void rightRotate(Node* x);

        // ==================== 插入：私有 helper ====================
        /// 插入修复：新结点 z 以红色插入后，若破坏"根叶黑"或"不红红"，在这里调整。
        /// 完整推导见笔记「四、插入」小节。
        void insertFixup(Node* z);

        // ==================== 删除：私有 helper ====================
        /// 用子树 v 替换子树 u 在其父结点中的位置（标准 BST 移植操作）
        void transplant(Node* u, Node* v);

        /// 返回以 node 为根的子树中最小关键字所在的结点
        Node* minimumNode(Node* node) const;

        /// 删除修复：真正被摘除位置的"双黑"问题在这里解决。
        /// 四个分支的完整推导见笔记「五、删除」小节。
        void deleteFixup(Node* x);

        /// 删除结点 nodeToDelete 的核心流程（BST 删除思路 + 红黑修复）
        void removeNodeHelper(Node* nodeToDelete);

        // ==================== 通用辅助 ====================
        void destroySubtree(Node* node);
        void printHelper(Node* node, int depth, char branch) const;
        int computeBlackHeightHelper(Node* node) const;
    };

    /// 演示函数只服务于 RBTree，放在 RBTreeADT 命名空间内、类外，

    void runAutoDemo();

## 🔍 三、操作一：查找 Search（代码块 2️⃣）

### 💭 思路

红黑树的查找**和普通 BST 完全一致**——毕竟红黑树的"颜色"只是为了约束插入/删除时的调整，并不改变查找的比较逻辑：从根出发，比 key 小就往左走，比 key 大就往右走，走到 `nil` 就说明没找到。

> [!tip] 一个小细节 因为用了哨兵 `nil`，循环条件可以直接写 `cur != nil`，不需要写成 `cur != nullptr`，也不需要在循环体内部特判"走到空节点了吗"——这也是哨兵设计在最简单的操作上就已经体现出来的便利。

### 🧩 头文件里的声明

```cpp
/// 从根出发做标准 BST 查找，命中返回结点指针，未命中返回 nil。
Node* searchHelper(KeyType key) const;

/// 查找关键字 key 是否存在（过程与普通 BST 查找完全一致）。
bool search(KeyType key) const;

/// 查找 key，并把命中结点的地址、颜色等信息写入 locationDesc（教学展示用）。
bool search(KeyType key, std::string& locationDesc) const;
```

### ⚙️ 实现文件里的代码

```cpp
RBTree::Node* RBTree::searchHelper(KeyType key) const {
    Node* cur = root;
    while (cur != nil && cur->key != key) {
        cur = (key < cur->key) ? cur->left : cur->right;
    }
    return cur; // 命中返回真实结点；未命中返回 nil
}

bool RBTree::search(KeyType key) const {
    return searchHelper(key) != nil;
}

bool RBTree::search(KeyType key, std::string& locationDesc) const {
    Node* node = searchHelper(key);
    if (node == nil) {
        locationDesc = "未找到";
        return false;
    }
    std::ostringstream oss;
    oss << "命中结点地址=" << static_cast<const void*>(node)
        << ", 颜色=" << (node->color == Color::RED ? "红" : "黑");
    locationDesc = oss.str();
    return true;
}
```

## ➕ 四、操作二：插入 Insert（代码块 3️⃣）

### 💭 完整思路链条

**Q：为什么新结点 z 要插成红色，而不是黑色？** 🤔

z 是叶子位置新插进来的，它自己不可能贡献"已经存在的路径"上的黑高——不管插成什么颜色，都不会破坏原本已经成立的"黑路同"，唯一需要担心的是**新增的这个点本身合不合规矩**：

- 如果插成黑色，z 所在路径的黑高必然比其它兄弟路径多 1，**每次插入都会违反"黑路同"**，都要调整；
- 如果插成红色，只有在"z 的父亲恰好也是红色"时才会违反"不红红"，其余情况**直接就是合法的红黑树**，不需要任何调整。

两权相较，插红色代价明显更小——这就是"z 初始颜色定为红色"的原因。

**Q：插成红色之后，可能出问题的地方有哪些？**

只有两处：① z 恰好是根（根必须黑色，冲突）；② z 的父亲 p 也是红色（红红相邻）。除此之外插入红色结点不会产生任何新问题，这也是为什么整个修复过程可以完全聚焦在"红红相邻"这一件事上。

**情况①怎么处理？** 如果 z 是根，直接染黑即可。这个特判甚至不需要单独写代码：哨兵 `nil` 恒为黑色，`z->parent->color == RED` 这个循环条件在 z 是根（`z->parent == nil`）时天然为假，循环根本不会执行，最后统一用 `root->color = BLACK` 收尾就自动覆盖了这种情况——**用数据结构的设计消解了一个特判**，这是本实现比较巧妙的一处。

**情况②怎么处理？先看叔叔 u 的颜色**

z 的父亲 p 是红色 ⇒ p 一定不是根（根是黑色）⇒ z 必然有爷爷 g，且 g 必然是黑色（红色结点的父亲不能是红色，这是上一轮循环已经维持好的不变式）。要解决"p、z 两个红色相邻"的矛盾，去看 g 的另一个孩子——z 的叔叔 u：

> [!note]- 🔴 u 是红色：怎么处理？ g 的两个孩子 p、u 都是红色，说明 g 这一层"还有富余"，可以直接把 **p、u 一起染黑、g 染红**——这一步不改变 g 子树对外的黑高（原来 g 黑色贡献 1 层，现在 p、u 各自多贡献 1 层黑色，两条路径正好抵消），但 g 现在变红了，如果 g 的父亲也恰好是红色，红红相邻的问题就从 z 这一层"平移"到了 g 这一层——把 g 当成新的 z，回到循环开头继续检查，直到某一层父亲是黑色，或者一路平移到根为止。

> [!note]- ⚫ u 是黑色（含 u 是 nil）：怎么处理？ g 这一层没有"红色富余"可用，没法简单整体变色，只能通过旋转局部调整树形，具体怎么转要看 z 相对 p、p 相对 g 的位置：
> 
> - 如果 z、p、g 三代拐了个弯（LR 或 RL 型），一次旋转没法把 z 转到最终位置，得**先在 p 上做一次旋转把它们"拉直"**成同一侧（LL 或 RR 型），代码里用 `z = z->parent` 完成这个视角切换；
> - 拉直成 LL/RR 之后（或者本来就是），**对 g 做一次旋转，同时把新的子树根（也就是 p）染黑、g 染红**。这一步完成后，这片子树对外暴露的黑高和调整前完全一样（原来 g 黑色贡献 1 层，现在 p 黑色贡献 1 层），红红相邻也解决了，且没有把问题传给上一层，**循环到此终止**。

对应讲义的说法：p 是 g 左孩子、u 是 g 右孩子是"第二类"；p 是 g 右孩子、u 是 g 左孩子是"第一类"，两类互为镜像。

### 🧩 头文件里的声明

```cpp
/// 插入关键字 key（默认约定：树中不存在重复关键字）。
void insert(KeyType key);

/// 插入修复：新结点 z 以红色插入后，若破坏"根叶黑"或"不红红"，在这里调整回来。
void insertFixup(Node* z);
```

### ⚙️ 实现文件里的代码

```cpp
void RBTree::insert(KeyType key) {
    // 约定树中不存在重复关键字，防御性查重。
    if (searchHelper(key) != nil) {
        return;
    }

    // 第一步：新建结点 z，颜色初始为红色（原因见上方思路链条）。
    Node* z = new Node(key, Color::RED, nil, nil, nil);

    // 第二步：标准 BST 插入，找到 z 应该挂的位置。
    Node* y = nil; // y 全程跟随 x 落后一步，最终就是 z 的父亲
    Node* x = root;
    while (x != nil) {
        y = x;
        x = (z->key < x->key) ? x->left : x->right;
    }
    z->parent = y;
    if (y == nil) {
        root = z; // 空树：z 就是新的根
    } else if (z->key < y->key) {
        y->left = z;
    } else {
        y->right = z;
    }

    // 第三步：插入后可能违反"根叶黑"或"不红红"，调用修复。
    insertFixup(z);
}

void RBTree::insertFixup(Node* z) {
    while (z->parent->color == Color::RED) {
        if (z->parent == z->parent->parent->left) {
            // 【第二类：p 是 g 的左孩子，u 是 g 的右孩子】
            Node* uncle = z->parent->parent->right;

            if (uncle->color == Color::RED) {
                // u 红色：p、u 变黑，g 变红，把 g 当成新的 z 继续向上检查
                z->parent->color = Color::BLACK;
                uncle->color = Color::BLACK;
                z->parent->parent->color = Color::RED;
                z = z->parent->parent;
            } else {
                // u 黑色，按 z 相对 g 的位置分两种情况
                if (z == z->parent->right) {
                    // LR：先对 p 左旋转化成 LL
                    z = z->parent;
                    leftRotate(z);
                }
                // LL（或 LR 转化后）：对 g 右旋，g 由黑变红，p 由红变黑，终止
                z->parent->color = Color::BLACK;
                z->parent->parent->color = Color::RED;
                rightRotate(z->parent->parent);
            }
        } else {
            // 【第一类：p 是 g 的右孩子，u 是 g 的左孩子】，与上面完全对称
            Node* uncle = z->parent->parent->left;

            if (uncle->color == Color::RED) {
                z->parent->color = Color::BLACK;
                uncle->color = Color::BLACK;
                z->parent->parent->color = Color::RED;
                z = z->parent->parent;
            } else {
                if (z == z->parent->left) {
                    // RL：先对 p 右旋，转化成 RR
                    z = z->parent;
                    rightRotate(z);
                }
                // RR（或 RL 转化后）：对 g 左旋，g 由黑变红，p 由红变黑，终止
                z->parent->color = Color::BLACK;
                z->parent->parent->color = Color::RED;
                leftRotate(z->parent->parent);
            }
        }
    }
    root->color = Color::BLACK; // 兜底保证"根叶黑"性质
}
```

## ➖ 五、操作三：删除 Delete（代码块 4️⃣）

删除是整棵红黑树里最绕、也是我们讨论问题最集中的一块，下面按"先摘除、再修复"两层展开。

### 🪓 5.1 第一层：怎么把结点从树上摘下来（BST 删除思路）

**Q：为什么不能直接把要删的结点摘掉？**

如果 `nodeToDelete` 左右孩子都存在，直接摘掉它会同时断开两棵子树，没法简单地把左右子树重新接起来。标准 BST 删除的套路是"偷梁换柱"：找一个值来覆盖 `nodeToDelete` 的位置，而**真正从树上被物理摘除的**，是结构更简单（度 ≤ 1）的另一个结点：

- 若 `nodeToDelete` 本身度数就 ≤ 1，不需要找替身，它自己就是"真正被物理摘除的结点"；
- 若度为 2，就找它的**中序后继**（右子树里最小的结点）——后继一定没有左孩子（否则那个左孩子比它还小，后继就不成立），所以后继度数必然 ≤ 1，用它顶替最省事。真正被物理摘除的，从 `nodeToDelete` 换成了这个后继。

> [!important] 一个容易被忽略的关键点 红黑树的颜色性质会不会被破坏、要不要调用 `deleteFixup`，**取决于"真正被物理摘除的结点"原来是什么颜色**，跟 `nodeToDelete` 原来的颜色反而没有直接关系——这也是代码里为什么要单独用一个变量（`splicedOutOriginalColor`）记录它，而不是直接看 `nodeToDelete->color`。

> [!note]- 💬 关于变量命名的讨论 早期版本沿用 CLRS 教材的记法 `z`/`y`/`x`，脱离教材语境很难看出谁是谁。后来改成了语义化命名：`nodeToDelete`（外部要删的结点，语义固定不变）、`splicedOutNode`（真正被物理摘除的结点，可能等于 `nodeToDelete`，也可能变成它的后继）、`replacement`（顶替者，可能是 nil）。改名之后代码可读性明显提升，但这只是命名层面的优化，算法逻辑完全没有变化。

### 🧩 头文件里的声明

```cpp
/// 删除关键字 key，返回是否删除成功（key 不存在则返回 false）。
bool remove(KeyType key);

/// 用子树 v 替换子树 u 在其父结点中的位置（标准 BST 移植操作）。
/// v 可能是 nil，此时会顺带把"父结点信息"写入 nil->parent，
/// 这是删除修复能正确处理"x 是 nil"这种情况的关键技巧。
void transplant(Node* u, Node* v);

/// 返回以 node 为根的子树中最小关键字所在的结点（一路往左走到底）。
Node* minimumNode(Node* node) const;

/// 删除结点 nodeToDelete 的核心流程（BST 删除思路 + 红黑修复）。
void removeNodeHelper(Node* nodeToDelete);
```

### ⚙️ 实现文件里的代码：摘除部分

```cpp
RBTree::Node* RBTree::minimumNode(Node* node) const {
    while (node->left != nil) {
        node = node->left;
    }
    return node;
}

void RBTree::transplant(Node* u, Node* v) {
    // 用子树 v 顶替子树 u 在其父结点中的位置。
    if (u->parent == nil) {
        root = v;
    } else if (u == u->parent->left) {
        u->parent->left = v;
    } else {
        u->parent->right = v;
    }
    // 无论 v 是不是 nil，都统一写入 parent——
    // 这是让 x 恰好是 nil 时也能在 deleteFixup 里正确定位父结点的关键技巧。
    v->parent = u->parent;
}

bool RBTree::remove(KeyType key) {
    Node* z = searchHelper(key);
    if (z == nil) {
        return false; // key 本不存在
    }
    removeNodeHelper(z);
    return true;
}

void RBTree::removeNodeHelper(Node* nodeToDelete) {
    Node* splicedOutNode = nodeToDelete;                   // 真正会被物理摘除的结点
    Color splicedOutOriginalColor = nodeToDelete->color;    // 决定要不要修复的关键
    Node* replacement;                                       // 顶替者（可能是 nil）

    if (nodeToDelete->left == nil) {
        replacement = nodeToDelete->right;
        transplant(nodeToDelete, nodeToDelete->right);
    } else if (nodeToDelete->right == nil) {
        replacement = nodeToDelete->left;
        transplant(nodeToDelete, nodeToDelete->left);
    } else {
        // 度为 2：改摘除中序后继
        splicedOutNode = minimumNode(nodeToDelete->right);
        splicedOutOriginalColor = splicedOutNode->color;
        replacement = splicedOutNode->right;

        if (splicedOutNode->parent == nodeToDelete) {
            replacement->parent = splicedOutNode;
        } else {
            transplant(splicedOutNode, splicedOutNode->right);
            splicedOutNode->right = nodeToDelete->right;
            splicedOutNode->right->parent = splicedOutNode;
        }
        // 让后继正式搬到 nodeToDelete 的位置——接管左子树、接管颜色。
        transplant(nodeToDelete, splicedOutNode);
        splicedOutNode->left = nodeToDelete->left;
        splicedOutNode->left->parent = splicedOutNode;
        splicedOutNode->color = nodeToDelete->color;
    }

    delete nodeToDelete;

    if (splicedOutOriginalColor == Color::BLACK) {
        deleteFixup(replacement);
    }
}
```

### 🌑 5.2 第二层："双黑结点"修复（deleteFixup）

**Q：双黑结点是什么？为什么会出现？**

删除黑色结点后，顶替它位置的结点 x（可能是 nil）**少继承了一层黑色**：树上其它路径的黑高都还是"正常值"，唯独经过 x 的这条路径比正常值少 1。我们没法凭空变出一层黑色，只能先记账——把 x 暂时看成一个"**双黑结点**"（自己已有的颜色之外，再欠一层黑色），账面上黑高又平了，但代价是这一侧"超支"了一层黑色，接下来的调整就是要么把超支的黑色转移走，要么把它彻底注销。

**Q：第一步该看哪？**

x 超支了一层黑色，离它最近、又能通过旋转 + 变色互相转移颜色而不惊动树其它部分的，就是它的兄弟 w。于是所有分类都围绕"w 有没有余粮可以借"展开：先看 w 本身颜色，再看 w 两个孩子（x 的两个侄子）的颜色。下面统一以 **x 是 p 的左孩子、w 是右兄弟**为例，右孩子情形完全对称（左右互换）。

> [!note]- 🔴 分支①：w 本身是红色 根据"不红红"，w 的两个孩子和 p 必然都是黑色。红色的 w 自己都不是黑的，没法直接借出黑色，这一步的目的是"**换一个能借的兄弟**"：对 p **左旋**，把 w 换成它原来的孩子（一定是黑色），同时 p 变红、旧 w 变黑，局部黑高不变。做完这一步，x 的新兄弟必然是黑色的，问题转化成了下面②③④之一，循环还没有终止。
> 
> ```cpp
> if (w->color == Color::RED) {
>     w->color = Color::BLACK;
>     x->parent->color = Color::RED;
>     leftRotate(x->parent);
>     w = x->parent->right; // 旋转后 x 的兄弟变了，重新取一次
> }
> ```
> 
> **💬 关于 `w = x->parent->right` 的疑问**：旋转会不会连 `x->parent` 一起改变？——不会。左旋只改变 p 的 `right` 指针和 p 的 `parent` 指针，完全不碰 p 的 `left` 指针，也不碰 x 本身，所以 `x->parent` 依然是同一个 p 对象。但 **p 的右孩子变了**（旋转前是旧 w，旋转后是旧 w 的左孩子），所以要重新取一次 `x->parent->right`，才能拿到 x 现在真正的新兄弟——这行代码里 `w` 是复用同一个变量名代表"x 当前兄弟"这个**角色**，不是某个固定结点。

> [!note]- ⚫ 分支②：w 黑色，且两个侄子都是黑色 局部（x、w 及其孩子）怎么倒腾颜色都凑不出多余的黑色，只能把"超支"上交给父结点：把 **w 染红**（w 这条路径黑高 -1，正好和 x 路径"本来就少 1"抵消，两条路径现在真的一样高了）。但这样一来 p 相对于它自己的兄弟那条路径又少了一层——双黑问题原封不动地转移到了 p 身上，令 `x = x->parent` 回到循环开头继续处理，直到 x 变成根或变红为止。
> 
> ```cpp
> if (w->left->color == Color::BLACK && w->right->color == Color::BLACK) {
>     w->color = Color::RED;
>     x = x->parent;
> }
> ```

> [!note]- 🌗 分支③④：w 黑色，且至少一个侄子是红色（能借） 要不要先"倒一次手"，取决于红色侄子离 x 是近还是远（w->left 是"近侄子"，w->right 是"远侄子"）：
> 
> **④ 远侄子红色（最理想）**：直接对 `x->parent` 做一次**左旋**，配合三处变色：
> 
> ```cpp
> w->color = x->parent->color;   // w 顶替 p 的位置，继承 p 对外的颜色
> x->parent->color = Color::BLACK; // p 染黑，给 x 补上欠的那层黑色
> w->right->color = Color::BLACK;  // 远侄子染黑，抵消旋转对右侧路径黑高的影响
> leftRotate(x->parent);
> x = root; // 循环终止
> ```
> 
> **③ 只有近侄子红色**：直接左旋不够用（顶上来的仍是黑色远侄子，补不上缺口），得先在 **w 内部做一次右旋**，把红色"搬到远侧"：
> 
> ```cpp
> w->left->color = Color::BLACK; // 近侄子染黑
> w->color = Color::RED;         // w 染红
> rightRotate(w);
> w = x->parent->right;          // 重新取新兄弟，局面变成了④的前提
> ```
> 
> 这一步只是 w 内部倒手（近侄子由红变黑、w 由黑变红，一进一出抵消），不影响外部黑高，做完之后紧接着走一遍④的终止步骤。

> [!note]- 🧮 「近侄子为什么不用管」的具体验算（黑高走一遍） 设近侄子子树黑高为 k（远侄子是红色，不贡献黑高，它下面的子树黑高也是 k；x 那一侧真实黑高也是 k，比正常少 1）。
> 
> **旋转前**：`p→x` 黑色数 = k；`p→w→近侄子` = 1+k；`p→w→远侄子` = 1+k。
> 
> **旋转后**（w 顶替 p 的位置、p 染黑、远侄子染黑）：`w→p→x` = 1+k ✅（补上了）；`w→p→近侄子` = 1+k ✅（没变）；`w→远侄子` = 1+k ✅（没变）。
> 
> 关键在于：近侄子从"w 的左孩子"变成"p 的右孩子"，路径上换了父亲，但 **w 从黑变红、p 从红变黑，两次变色正好抵消**，所以近侄子头顶的黑色总数根本没变——它不需要也不应该被特殊处理。

> [!note]- 🔚 关于 `x = root` 为什么能退出循环 循环条件是 `while (x != root && x->color == Color::BLACK)`，`x = root` 让 `x != root` 直接变假，效果等价于 `break`。之所以不直接写 `break`，是沿用 CLRS 的经典写法：循环外的收尾语句 `x->color = Color::BLACK;` 恰好会把 `root` 再染一次黑（本来就应该是黑色，无害），顺带不需要专门代码去跳过它。
> 
> **💬 会不会因此产生"多个 root"？**——不会。`x = root` 只是让局部指针变量 `x` 这个"标签"也指向 `root` 当前指向的同一个对象，**没有创建新结点，也没有修改任何结点的 `parent`/`left`/`right` 字段**，更没有修改 `root` 成员变量本身指向谁。区分标准就是：**改指针变量自己存的地址值**（`x = root;`）只影响这个指针接下来指向哪，跟外部无关；**改指针指向的对象内部字段**（`x->color = ...`、`x->parent->left = y` 这种"解引用后赋值"）才是真正修改共享状态、会影响树结构的操作。真正保证"树只有一个根"的不变量，是全树里 `parent == nil` 的结点有且只有一个——而 `x = root;` 根本没碰任何结点的 `parent` 字段，这个不变量从头到尾都没被破坏。

### ⚙️ 实现文件里的代码：修复部分

```cpp
void RBTree::deleteFixup(Node* x) {
    while (x != root && x->color == Color::BLACK) {
        if (x == x->parent->left) {
            Node* w = x->parent->right; // w：x 的兄弟

            if (w->color == Color::RED) {
                w->color = Color::BLACK;
                x->parent->color = Color::RED;
                leftRotate(x->parent);
                w = x->parent->right;
            }

            if (w->left->color == Color::BLACK && w->right->color == Color::BLACK) {
                w->color = Color::RED;
                x = x->parent;
            } else {
                if (w->right->color == Color::BLACK) {
                    w->left->color = Color::BLACK;
                    w->color = Color::RED;
                    rightRotate(w);
                    w = x->parent->right;
                }
                w->color = x->parent->color;
                x->parent->color = Color::BLACK;
                w->right->color = Color::BLACK;
                leftRotate(x->parent);
                x = root;
            }
        } else {
            // x 是右孩子：与上面完全对称，左右互换
            Node* w = x->parent->left;

            if (w->color == Color::RED) {
                w->color = Color::BLACK;
                x->parent->color = Color::RED;
                rightRotate(x->parent);
                w = x->parent->left;
            }

            if (w->right->color == Color::BLACK && w->left->color == Color::BLACK) {
                w->color = Color::RED;
                x = x->parent;
            } else {
                if (w->left->color == Color::BLACK) {
                    w->right->color = Color::BLACK;
                    w->color = Color::RED;
                    leftRotate(w);
                    w = x->parent->left;
                }
                w->color = x->parent->color;
                x->parent->color = Color::BLACK;
                w->left->color = Color::BLACK;
                rightRotate(x->parent);
                x = root;
            }
        }
    }
    x->color = Color::BLACK; // 把 x 染黑：双黑 -> 单黑，多余的黑色被"吸收"
}
```

## 🧾 六、编译踩坑记录（额外收获）

这部分不是算法本身，但花的排查时间不比算法少，值得单独记一笔 ⚠️

### 🐛 坑一：编译期中文乱码（一堆 C4819 / C2001 / C2143）

**现象**：源文件明明没写错，Visual Studio 却报了一大串"常量中有换行符""语法错误：缺少 `;`"之类看起来毫不相关的错误。

**根因**：文件是**无 BOM 的 UTF-8**。cl.exe 在没有 BOM 标记时，会按**系统代码页**（中文 Windows 通常是 GBK/936）去解析源文件；UTF-8 里的中文是多字节序列，用 GBK 硬解会把字节流读乱，撞上某些字节组合被误认成引号/反斜杠，从而炸出一连串语法错误。

**修法**（二选一）：

1. 项目属性 → C/C++ → 命令行 → 附加选项，加 `/utf-8`；
2. 给源文件本身加 UTF-8 BOM（`EF BB BF`），VS 就能自动识别编码，不用再靠系统代码页去猜。

### 🐛 坑二：加了 `/utf-8` 后编译对了，控制台却乱码了

**根因**：`/utf-8` 让编译器正确地把源文件按 UTF-8 解析了，生成的字符串字面量也是 UTF-8 字节；但 **Windows 控制台默认还是按 GBK 去解释输出的字节**，两边编码这才第一次真正对上了号——不是"没对上"，恰恰是"终于对齐了源码编码"之后，才暴露出控制台这一层的错位。

**修法**：在 `main()` 开头设置控制台代码页：

```cpp
#ifdef _WIN32
#include <windows.h>
#endif

int main() {
#ifdef _WIN32
    SetConsoleOutputCP(CP_UTF8);
    SetConsoleCP(CP_UTF8);
#endif
    // ...
}
```

`#ifdef _WIN32` 保证这段代码只在 Windows 上生效，不影响跨平台编译。

### 🤔 坑三：为什么自己写的代码从来没遇到过这个问题？

追问到底发现：**不是"新建 vs 下载"的区别，而是字符本身**。GBK（代码页 936）能表示的字符是**有限集合**，普通汉字和常规标点都在这个集合里，所以自己在 VS 里敲中文注释、保存，编辑器全程用 GBK，从头到尾没有分歧点。但一旦粘贴进来的内容里混入了 GBK 字符集之外的符号（比如某些排版用的长破折号、特殊箭头），VS 就没法把整个文件"无损"存成 GBK 了，于是**悄悄自动切换成不带 BOM 的 UTF-8 保存**——这个切换是编辑器背着你做的，肉眼完全看不出来，但后果就是文件编码和系统默认代码页第一次产生了错位。

> [!note] 三个坑的共同结论 不带 BOM 的 UTF-8 源文件本身就是个隐患，只是"够不够触发"全凭注释里用没用到 GBK 字符集之外的符号。一劳永逸的做法：**源文件统一带 BOM + 项目统一加 `/utf-8` + `main()` 里统一设置控制台代码页**，把这一整条链路的编码假设锁死，不用再"看运气"。

## 🎓 七、总结

### ✅ 核心回顾

- 红黑树是 BST 在"严格平衡（AVL）"和"完全不平衡（普通 BST）"之间找的一个**折中点**：用颜色约束代替高度约束，插入/删除的旋转次数更少，更适合动态查找场景。
- **五条性质**（非红即黑 / 根黑 / 叶黑 / 不红红 / 黑路同）共同保证了树高不超过 2·log(n+1)，查找、插入、删除都是 **O(log n)**。
- **哨兵 nil** 让"空结点"天然拥有颜色，统一了插入/删除/旋转的边界处理，是教科书级实现的标配技巧。
- **插入**：新结点恒定插成红色（代价最小），只需处理"根"和"父亲红色"两种情况，父亲红色时再按叔叔颜色（红→整体变色上移；黑→旋转，LR/RL 先拉直成 LL/RR）分类处理。
- **删除**：先按 BST 思路摘除（度为 2 时转化成删除中序后继），若被摘除的结点是黑色，则产生"双黑"，通过兄弟 w 的颜色和侄子颜色分四种情形（红兄弟→换兄弟；黑兄弟两黑侄子→上移；黑兄弟单红侄子→倒手转化；黑兄弟远红侄子→一次旋转终止）逐步消解。
